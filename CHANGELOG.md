# Changelog

## 0.27.55 — 2026-09-14

- **Conversational Ask Netra: short-lived, bounded multi-turn memory for `/api/v1/ai/ask`.** Every AI-answered question — web "Ask Netra" card, `netractl ai ask`, the `netra_ai_ask` MCP tool, ChatOps's `/netra ask` — has been fully stateless: no way to ask "what about the second one?" without repeating full context. This closes that gap for the two surfaces where a "conversation" already naturally exists — the web card and ChatOps — while leaving the CLI and MCP tool stateless by design (a one-shot CLI process has no session to hang memory on, and an MCP tool call already has the calling agent's own conversation as its memory).
  - New `internal/ai/conversation.go`: an in-process, bounded, TTL-based store (the same package-level-singleton shape `internal/ai/digest.go`'s shared fingerprint state already uses, not a new persistence layer) — 6 turns per conversation (oldest dropped first), a 30-minute idle TTL, and a soft 2000-conversation global cap past which new conversations are silently not remembered rather than erroring the request. Turn text is clipped to ~240 runes before storage so a long or repeated question can't grow the LLM prompt unboundedly across turns.
  - `ai.Answer` gains a `conversationID` parameter (backward compatible — `""` behaves exactly as before this release); `Brief`/`AskRequest` gain a `conversationId` field, entirely opt-in. `Provider.Rewrite` gains a `history []Turn` parameter, appending a bounded "prior turns in this conversation" block to the LLM prompt with an explicit system-prompt line that prior turns are for resolving references only, never new cluster data.
  - New `POST /api/v1/ai/forget` (`{"conversationId": "..."}` → `{"ok": true}`) clears one conversation's memory — the HTTP seam ChatOps's new `/netra forget` needs, since `internal/chatops` is documented as never importing `internal/ai` internals directly and must go through the API like every other chatops call.
  - ChatOps: `Dispatch` gains a `conversationKey` parameter, threaded to the new `ask`/`forget` cases only. Slack computes it from the slash command's own `channel_id`+`user_id`; Teams (whose `teamsActivity` struct didn't previously parse `conversation.id`) now does, computing it from `conversation.id`+`from.id`. Neither provider needs a new command to get multi-turn memory — the same channel+user asking follow-ups in `/netra ask` just works.
  - Web: `AskNetra.tsx`'s single replaced-each-time answer becomes an actual scrollback thread (capped display of the last 8 exchanges); a `conversationId` is minted client-side (`crypto.randomUUID()`) on the first question in a tab and sent on every subsequent one; a new "New conversation" button resets it.
  - `docs/ai.md` gains a "Conversation memory" section (scope, bounds, what's stored); `docs/chatops.md` gains the `/netra forget` row and a matching section.
  - Tests: `internal/ai/conversation_test.go` (record/lookup round trip, turn-cap ring behavior, TTL expiry via an injectable clock, global-cap graceful degrade, `ClearConversation`), `internal/ai/ask_test.go` (conversation ID echoed, turns recorded on the heuristic path, history actually reaches the provider prompt on a second turn but not the first), `internal/api/ai_test.go` (new — `aiAsk`/`aiForget` handler round trips; no prior HTTP-layer tests existed for any `ai/*` route), `internal/chatops/commands_test.go`/`handler_test.go`/`teams_handler_test.go` extended for `ask`'s `conversationId` pass-through, the new `forget` command, and end-to-end confirmation that the computed key is stable per (channel, user) and distinct across users on both Slack and Teams.
  - Manually verified end to end against a local `netrad`: `conversationId` round-trips through `POST /api/v1/ai/ask`, and `POST /api/v1/ai/forget` clears it.
- Version bumped to 0.27.55 across all six tracked locations; `web/package-lock.json` regenerated.

## 0.27.53 — 2026-09-14

- **The new `bpf/integration` CI job (0.27.52) failed on its actual first real GitHub Actions run — fixed, and the fix itself surfaced a second, more fundamental finding.** Cross-compiling and `go vet`-ing the package from this project's non-Linux dev environment could only prove it type-checked, never that it would actually pass on a real runner; it didn't, twice, for two different real reasons.
  - **Failure 1: `loadCollection` didn't replicate the L7 verifier-rejection fallback.** It loaded the whole compiled object unconditionally, hitting the already-documented, standing `netra_l7_cgroup_egress`/`ingress` verifier rejection (`docs/l7-metadata.md`) on the runner's kernel — the exact thing `internal/agent.loadAndAttach` already works around on a real node (strip those two programs from the spec and retry). Fixed by giving the test harness the same fallback. None of these tests exercise L7/DNS behavior, so dropping those two programs never affects what's under test.
  - **Failure 2, after fixing failure 1: a genuine `BPF_PROG_TEST_RUN` constraint, not a bug.** With the L7 fallback in place, `TestSynDropCIDR`/`TestSynDropExactIP` (targeting `netra_egress`, a `tc`-hook program) passed cleanly on the real runner — this project's first-ever confirmed real-kernel proof of the SYN-drop behavior. But `TestNetPolPortOnly` (targeting `netra_cgroup_egress`, a `cgroup_skb`-hook program) still failed every case that depended on a rule actually matching. Diagnostics added to isolate the cause (`netpol_v2_enabled` readback, computed `cgroup_id`, a same-key Go-side map readback immediately after writing) confirmed the Go-side map-key encoding was byte-for-byte correct — the real cause is that `bpf_get_current_cgroup_id()` (what `netpol_v2_lookup4` keys every lookup on) reads the cgroup associated with the packet's owning *socket*, and a synthetic `BPF_PROG_TEST_RUN` packet has no real socket behind it, so the helper returns 0 throughout. `cilium/ebpf`'s `RunOptions` has no field to inject cgroup context — there is no userspace-side fix. `netra_egress`'s tc-hook path never has this problem (`cgroup_id` is unconditionally 0 there by design, so nothing about its behavior depends on a value `BPF_PROG_TEST_RUN` can't provide).
  - `TestNetPolPortOnly` replaced with `TestNetPolRuleKeyEncoding`: no kernel invocation, but a real, still-valuable regression guard for the exact class of bug this whole effort was chasing — verified against the live diagnostic byte dump from the failing CI run itself (`cgroup_id=6520`, `peer=1.2.3.4`, `port=443` reproduced exactly). Live-cluster traffic remains the only way to prove `netpol_v2_lookup4`'s full runtime behavior end-to-end (`docs/native-netpol.md`), same as before — this was never actually closed by the 0.27.52 CI harness for the cgroup-hook path specifically, only for the tc-hook path (SYN-drop).
  - Removed now-dead helpers (`buildCgroupFrame`, `cgroupAllow`/`cgroupDeny`, `selfCgroupID`) rather than leaving them unused.
  - Verified: this is the first `bpf/integration` change actually confirmed against real GitHub Actions CI (not just local cross-compilation) — `ebpf` job green end-to-end: L7 fallback engages and logs as expected, `TestSynDropCIDR`/`TestSynDropExactIP` pass for real on a real kernel, `TestNetPolRuleKeyEncoding` passes. `go build/vet/test ./...` unaffected.
- Version bumped to 0.27.53 across all six tracked locations; `web/package-lock.json` regenerated.

## 0.27.52 — 2026-09-14

- **First-ever kernel-execution-level BPF test harness, plus a real bug it would have caught immediately.** 0.27.51's live-cluster verification left two behaviors "not cleanly proven" (SYN-drop-CIDR's new-vs-established distinction, NetPol port-only's live traffic admission) — both turned out to be test-fixture limitations of testing kernel packet-filtering through real network I/O on a live, shared, flaky host, not anything provable or disprovable about the code itself. The fix: stop trying to prove kernel behavior through the network stack, and test the compiled BPF program directly against synthetic packets instead.
  - New `bpf/integration/` package (`//go:build linux && bpfintegration`, opt-in tag so it never runs as part of plain `go test ./...` anywhere, including this project's own non-Linux dev environment): loads the real compiled `bpf/netra_tc.o` via `cilium/ebpf`'s `Program.Test()` (backed by the kernel's `BPF_PROG_TEST_RUN`) and runs it against hand-packed synthetic Ethernet+IPv4+TCP / raw IPv4+TCP frames — a real kernel verifier, real BPF maps, real program execution, zero network I/O. This is the first time any BPF program in this project has been executed and asserted on by an automated test; every eBPF feature to date has only ever been confirmed by hand, live, on a real cluster.
  - `TestSynDropCIDR`/`TestSynDropExactIP` (`bpf/integration/syndrop_cidr_test.go`): proves the exact case live testing couldn't isolate — SYN-drop's `!syn_new` gate is a pure TCP-flag check on the *current packet*, not a conntrack/"established" check, so a fresh empty conntrack map doesn't affect the verdict at all. Deterministically confirms full-block control, new-SYN-still-dropped-when-flagged, and non-SYN-let-through-when-flagged, for both the CIDR and (as a bonus first-ever regression guard) the original exact-IP maps.
  - `TestNetPolPortOnly` (`bpf/integration/netpol_portonly_test.go`): proves `netpol_v2_lookup4`'s three-step fallback ordering directly — no rule falls through to allow, exact peer+port denies, the new any-peer+exact-port wildcard denies, and (the case that matters most) an exact match takes priority over a coexisting port-only rule while the port-only rule still applies to every *other* peer on that port. Resolves `bpf_get_current_cgroup_id()`'s test-time value by reading `/proc/self/cgroup` and `stat()`-ing the corresponding `/sys/fs/cgroup` path for its inode (cgroup v2's cgroup ID *is* that inode) — the value isn't injectable through `RunOptions`, so the test seeds `netpol_rules4` keyed to its own real process cgroup.
  - **Found a real, pre-existing byte-order bug while designing the map-key encoding these tests needed to get exactly right**: `internal/agent.applyNetPolV2`'s `ruleKey{... Port: r.Port ...}` stored the port field in the host's native (little-endian) byte order, because `ruleKey` is a typed Go struct and `cilium/ebpf` marshals typed struct fields using native encoding — but `netpol_v2_lookup4` (`bpf/netra_tc.c`) compares against `dport`, copied verbatim from the packet's big-endian wire bytes with no swap. For any non-palindromic port (443, 8080, 22 — essentially every real port), the stored key's bytes never matched what the kernel would ever look up, silently making **every** NetPol v2 rule with a specific port (not just the new port-only ones) a dead entry that never fired. `Peer` already handled this correctly via a `native.Uint32(ip.To4())` round-trip trick; `Port` now gets the equivalent `binary.BigEndian.PutUint16` + `native.Uint16` treatment. This had shipped since NetPol v2's original port-matching support and was invisible to prior testing because real usage predominantly used port=0 ("any port") rules, whose bytes are the same in either byte order — likely also the true root cause behind 0.27.51's live-cluster NetPol port-only test showing no effect (previously attributed only to `kubectl debug` ephemeral-container cgroup attribution, which remains a real, separate limitation but no longer the only explanation).
  - CI (`.github/workflows/ci.yml`'s `ebpf` job): builds the test binary as the normal runner user (so root never needs write access to the Go build/module cache), then runs it under `sudo` — `CAP_BPF`/`CAP_SYS_ADMIN` is required to create real BPF maps/programs and invoke `BPF_PROG_TEST_RUN`, the same privilege level any real BPF loader (including `internal/agent`'s, on a live node) always needs.
  - `docs/syn-drop.md`/`docs/native-netpol.md` updated to point at this automated coverage instead of "still outstanding."
  - Verified: `go build/vet/test ./...` (unaffected — new package is tag-gated out), `GOOS=linux go build/vet -tags=bpfintegration ./bpf/integration/...` and `GOOS=linux go test -tags=bpfintegration -c` all clean (cross-compiled from this project's non-Linux dev environment — the tests themselves cannot be *run* here, only compiled and type-checked; actual execution requires the real Linux kernel CI now provides, matching this project's existing honesty about BPF verification only being checkable in CI or on a real Linux host).
- Version bumped to 0.27.52 across all six tracked locations; `web/package-lock.json` regenerated.
