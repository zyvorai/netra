Ship plan and product boundary

Ship what you can support

The commercial proposal should reflect what is actually ready to operate and support.

Now: Community

Keep and harden the current repository: eBPF dataplane, firewall, diagnostics, capture, HA, exports, AI/MCP, ChatOps, GitOps, and in-cluster fleet.

Enterprise v1

Multi-cluster controller, OIDC/SAML/SCIM, scoped RBAC, durable storage, policy governance, compliance evidence, managed connectors, certified build pipeline, and support operations.

Post-GA

MSP multi-tenancy, delegated customer portals, white-label, cross-region federation, advanced behavior analytics, and FIPS validation after technical and commercial demand is proven.

Release gates before the first Enterprise contract

  • Define Community and Enterprise repositories, build provenance, and commercial licence enforcement under the Zyvor Production License.
  • Publish a support matrix for Linux kernels, Kubernetes versions, CNIs, CPU architectures, and storage backends.
  • Create signed release artifacts, SBOMs, a CVE response policy, upgrade/rollback procedures, and an enterprise release channel.
  • Run live-kernel verification for features documented as build/test verified but not yet live-kernel verified.
  • Establish support intake, severity definitions, on-call ownership, escalation paths, and customer communication templates.
  • Attach a module availability schedule to every proposal. Do not contract FIPS, MSP multi-tenancy, or roadmap features before they are deliverable.
